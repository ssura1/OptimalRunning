# Apps/WatchLegacy — the Series 3 tier

> ## ❄️ Frozen as of 2026-08-09 — maintained, not developed
>
> This tier is in **maintenance mode** ([ADR-015](../../docs/design.md#adr-015)). It receives **no
> new feature work**. It keeps building, and it keeps running in CI.
>
> | Change | Allowed |
> |---|---|
> | Keeping it compiling against a shared `Core` change | **yes — this is the point** |
> | Fixing a defect in what it already does | yes |
> | A CI or toolchain repair | yes |
> | Implementing a feature `Apps/WatchModern` gains | **no** |
> | Porting a new screen, gesture or metric across | **no** |
>
> **Why it is still here rather than deleted.** Deletion is already the planned response to
> [R-1](../../docs/requirements.md#11-risks) and costs one directory and one CI job — but R-1 has
> not arrived. Xcode 26 still builds a watchOS 8 deployment target. Meanwhile the `legacy-support`
> CI job earns its place for a reason unrelated to Series 3: it replays the shared fixtures against
> the shared goldens on a *different toolchain* from every other job, so a `Core` change that
> breaks tier equivalence is caught there first.
>
> **Why it stopped receiving features.** `Apps/WatchModern` moved to a watchOS 26 floor
> ([ADR-014](../../docs/design.md#adr-014)), putting eighteen major versions between the tiers.
> Every feature ported here would have to be rewritten against watchOS 8 idioms for hardware that
> stops building in about eight months.
>
> **Commit convention.** A commit touching this directory carries a **`[legacy]` prefix** in its
> subject, so which tier a push belongs to is unambiguous:
>
> ```
> fix(watch): [legacy] keep the segment encoder compiling after the Core rename
> ```

watchOS 8.0, armv7k. Its own Xcode project and bundle identifier, sharing nothing with
`Apps/WatchModern` but `Core` ([AC-FR-K-1-4](../../docs/requirements.md), enforced by
`Tools/check-tier-isolation.sh`).

**If you own a Series 3 and want to put this on it, start at

## Layout

```
LegacySupport/          local SwiftPM package — all testable logic. Where the tier really lives.
Sources/                the WatchKit extension: SwiftUI views + framework adapters. Thin by design.
Tests/                  T-072's on-device performance suite. Meaningless off-device.
project.yml             xcodegen source of truth. Regenerate; do not hand-edit the .xcodeproj.
```

Two Xcode targets, not one: `application.watchapp2` containing a `watchkit2-extension`. The
single-target watch app is identified by the `WKApplication` Info.plist key, which is **watchOS 9+** —
a single-target bundle with an 8.0 deployment target produces something Series 3 will not launch.

## The one thing to understand before changing anything here

**There is no watchOS 8 simulator.** Xcode 26 ships no such runtime, and the only installed watchOS
runtime is 26.5. So this tier has exactly two places where code can be verified:

1. `swift test --package-path Apps/WatchLegacy/LegacySupport` — the macOS host. Fast, real, and the
   only automated coverage this tier will ever have.
2. A physical Series 3.

There is nothing in between. That single fact shapes the whole tier: `LegacySupport` deliberately
carries more than `WatchSupport` does, and anything left in `Sources/` is verifiable on hardware only.
When adding code here, the question is always *can this go in the package instead?*

## Why the duplication is deliberate

Almost every file in `LegacySupport` has a near-twin in `Apps/WatchModern/WatchSupport`. That is
[ADR-002](../../docs/design.md) and AC-FR-K-1-4, not an accident, and the gate will fail if you
"clean it up" by sharing a file.

The reasoning: what is duplicated is *orchestration* — which sensor wins, how a screen is laid out.
What is **not** duplicated is every judgement: zone, target, grade, alert timing, interval state, all
of which live in `Core` and are called from both tiers. The payoff is that deleting this directory
when the Series 3 window closes cannot regress the Modern tier ([R-1](../../docs/requirements.md#11-risks)).

The cost is drift risk ([R-7](../../docs/requirements.md#11-risks)), and duplication does nothing to
prevent it. What prevents it is tests that actively compare the tiers:

| What is compared | How | Where |
|---|---|---|
| Engine output, all 7 fixtures | whole-`EngineGolden` equality, **no tolerance**, against the same committed goldens Core and Modern use | `LegacySupport/Tests/.../TierEquivalenceTests.swift` |
| Rendered interval screen | committed presentation golden, generated by Modern, compared by both | `.../PresentationEquivalenceTests.swift` |
| HealthKit segment boundaries | asserted against the engine golden's transition times | `.../SegmentEventTests.swift` |
| The uploaded envelope | Legacy's real transmitted bytes, ingested by PhoneSupport's T-049 assertions | `Fixtures/legacy-tier-envelope.payload` |

Neither tier imports the other. Equality with a shared committed artifact is transitive, which is what
makes AC-FR-K-1-2 satisfiable without violating AC-FR-K-1-4.

## Regenerating the goldens

The **Modern tier owns** the presentation golden:

```
REGENERATE_PRESENTATION_GOLDEN=1 swift test --package-path Apps/WatchModern/WatchSupport
```

This tier has no regeneration path, deliberately. If a Legacy test goes red, the fix is never to
regenerate from Legacy — that turns a caught divergence into the new expectation.

The transmitted-envelope artifact is owned here:

```
REGENERATE_LEGACY_PAYLOAD=1 swift test --package-path Apps/WatchLegacy/LegacySupport
```

Re-run `PhoneSupport`'s tests afterwards; they ingest that exact file.

## Build and test

```
cd Apps/WatchLegacy && xcodegen generate

# The tier's logic — the job that matters.
swift test --package-path Apps/WatchLegacy/LegacySupport

# The watchOS 8 / armv7k build.
xcodebuild -project Apps/WatchLegacy/OptimalRunnerLegacy.xcodeproj \
  -scheme OptimalRunnerLegacy -destination 'generic/platform=watchOS' \
  CODE_SIGNING_ALLOWED=NO build
```

`Tests/PerformanceTests.swift` is **not** in the scheme's test action. Its numbers mean nothing on a
fast machine, and running it there would create the impression NFR-1/2/3 are covered when they are not.
Run it explicitly, on the device.

## What is verified, and what is not

`swift test` covers 39 tests here: the fixture replay against the shared goldens, distance fusion,
GPS-drought fallback, capture durability under real `SIGKILL`, segment boundaries, the metrics matrix
across every zone × palette × case size, cross-tier presentation equivalence, and envelope production.

Not covered, and why, in `Tools/manual-test-protocol.md`. The two entries worth knowing up front:

- **§1 — the fixture replay has not been run on Series 3 hardware.** It passes on the macOS host's
  arm64 FPU. Series 3 is armv7k, a genuinely different architecture, and no simulator could settle it
  either. This is the first thing to verify once hardware is to hand.
- **§5 — paired-device sync needs two physical devices.** An iOS test run logs
  `WCErrorCodeDeviceNotPaired` on every context update, which is the honest result rather than a
  warning to suppress.
