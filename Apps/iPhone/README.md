# iPhone

`OptimalRunner.xcodeproj`, iOS 17.0+, iPhone only. Generated by
[xcodegen](https://github.com/yonaskolb/XcodeGen) from `project.yml` — **do not hand-edit the
`.xcodeproj`**; edit `project.yml` and run `xcodegen generate` from this directory.

```sh
xcodegen generate

# The fast loop — the tier's logic, no simulator, ~11 s. Run this first.
swift test --package-path PhoneSupport

# The platform loop — the same logic compiled for iOS, plus the app build.
xcodebuild test -project OptimalRunner.xcodeproj -scheme OptimalRunner \
  -destination 'platform=iOS Simulator,name=iPhone 17'
```

## Where the logic lives

This target owns SwiftUI, Swift Charts, MapKit, and the two framework adapters that cannot be
usefully faked at this level (`WCSession`, `HKHealthStore`). Everything else is in
`PhoneSupport/`, a local Swift package testable on the macOS host — see
[ADR-013](../../docs/design.md#adr-013).

| `PhoneSupport` file | Owns | Task |
|---|---|---|
| `Persistence/Models.swift` | The SwiftData schema and its migration plan | T-053 |
| `Persistence/RunStore.swift` | `RunRepository`, the blob-free list projection | T-053, T-054 |
| `Persistence/AggregateRepository.swift` | The statistics cache and its rebuild oracle | T-061 |
| `Persistence/RunLibrary.swift` | The single write surface — store and totals stay in step | T-053, T-061 |
| `Ingest/EnvelopeIngestor.swift` | Validate, upsert by `runID`, update totals, ACK/NACK | T-049 |
| `Health/BackfillService.swift` | Degraded reconstruction, and never overwriting better data | T-051 |
| `Analysis/RunAnalysis.swift` | Charts, zones, splits, reps, route segments | T-056…T-060 |
| `Downlink/PhoneContextPublisher.swift` | The one application context, plus `ProfileRepository` | T-050, T-062 |
| `Profile/PaceDerivation.swift` | Riegel normalisation and pace suggestions | T-062 |

### Why `Tests/` exists as well

The package suite runs on the macOS host — fast, and proving behaviour on the wrong platform.
`Tests/` re-runs a slice compiled for **iOS**, which is where storage behaviour can genuinely
differ. It re-measures Core Data's externalisation threshold specifically, because T-053's design
note depends on that number and it was first measured on macOS. Wave 2 learned this the expensive
way, when an API that compiled on the macOS test host turned out not to exist on watchOS.

## Manual verification protocol

Everything below is **not covered by any automated test**. The first group is the important one:
WatchConnectivity between two paired devices is not something the Simulator models — an iOS test
run logs `WCErrorCodeDeviceNotPaired` on every `updateApplicationContext`, which is the honest
answer rather than a warning to suppress.

### Requires two paired physical devices

| What | Why automation cannot reach it | Requirement |
|---|---|---|
| A finished run actually transfers watch → phone | The whole `WCSession` file-transfer path. Both endpoints are tested against fakes; the wire between them is not simulable. | AC-FR-E-1-1 |
| Delivery within 60 s of reachability | A property of the system's own transfer scheduling between paired devices. | AC-FR-E-1-7 |
| A payload queued while the phone is away transfers on reconnect | Real reachability transitions. The *decision* logic is tested against an injectable transport; the transition is not. | AC-FR-E-1-2, DEG-7 |
| An acknowledgement reaches the watch and deletes its payload | Round trip through the real application context. | AC-FR-E-1-2 |
| A profile edit on the phone appears on the watch | Same channel, other direction. | AC-FR-I-1-6 |
| The watch keeps running correctly with the phone genuinely off | Storage behaviour is tested by relaunching a store; "phone genuinely absent for a long run" is not. | AC-FR-I-1-6 |
| Days of queued runs all arrive after a long disconnection | DEG-7 at realistic scale. | DEG-7 |

### Requires HealthKit authorization on a device

| What | Why | Requirement |
|---|---|---|
| Backfill finds real `HKWorkout`s | Needs an authorized store with real workout history; the Simulator's HealthKit is limited and CI cannot grant authorization. | AC-FR-E-1-6 |
| Route data from `HKWorkoutRoute` | Not fetched by the current query — see the note in `HealthKitWorkoutSource`. | AC-FR-E-1-6 |

### Requires a simulator, but not hardware

| What | Why | Requirement |
|---|---|---|
| The statistics screen renders in under 300 ms with 1 000 runs | The data path is O(1) by construction — one decoded cache blob — so what remains is SwiftUI layout, which needs a stopwatch. | NFR-5 |
| The run list scrolls at 60 fps with 1 000 runs | The *fetch* is proved not to read blobs; frame rate is a rendering property. | AC-FR-F-1-3 |
| Charts are legible in greyscale | Visual judgement. Every zone row carries its glyph, which is the structural half. | AC-FR-F-2-9 |
| VoiceOver reads chart values | An `AXChartDescriptor` is supplied and can be inspected in the Accessibility Inspector; that it *reads well* is a judgement. | AC-FR-F-2-2 |
| The route map renders and is omitted from any diagnostic export | There is no export path yet, so the second half is currently vacuously true. | AC-FR-F-2-7, NFR-17 |
| Onboarding end to end on a fresh install | Store state, not logic. Each step's effect is unit-tested. | FR-I-1 |

## Layout

| Directory | Owns |
|---|---|
| `Sources/App` | Entry point, the five-tab shell, onboarding gate |
| `Sources/DesignSystem` | `ORColor` bridged to SwiftUI, formatting. The **only** place a colour is named |
| `Sources/Features/RunList` | The run list and its filters |
| `Sources/Features/RunDetail` | Charts, zones, splits, reps, map |

| `Sources/Features/Profile` | Paces, units, palette, haptics, the health notice |
| `Sources/Features/Onboarding` | First-run setup |
| `Sources/Features/Plan`, `Library` | Deferred (P1/P2) — the tabs exist and say so |
| `Sources/Transport` | The `WCSession` conformer. No decisions |
| `Sources/Health` | The `HKWorkout` query. No decisions |
| `PhoneSupport/` | The tier's logic ([ADR-013](../../docs/design.md#adr-013)) |
| `Tests/` | iOS platform smoke suite — see above |
